## Why this matters

The currently installed no-Metro APK is a self-contained debug artifact. The
generated Android project signs its release type with the debug key, and no
protected workflow produces the release APK consumed by the strict evidence
verifier. A release candidate needs a repeatable production-like APK for device
testing, a store AAB, non-debug signing, an embedded JavaScript bundle, exact
commit/SHA provenance, and a detached attestation from the already pinned trust
root.

## Steps

### Step 1: Define two explicit release profiles

In `mobile/eas.json`, keep development separate and define:

- `release-apk`: `developmentClient: false`, `distribution: internal`, Android
  `buildType: apk`; this is the no-Metro artifact installed for physical release
  verification;
- `production`: `distribution: store`, Android `buildType: app-bundle`; this is
  the Play artifact and must extend or share the same release environment.

Do not set `withoutCredentials: true` on either. Configure app-version source
deliberately and document it. Use EAS-managed or protected externally supplied
Android credentials for the stable package `com.twinotify.app`.

**Verify**: resolve both profiles with EAS config and assert APK versus AAB.

### Step 2: Add a fail-closed standalone artifact verifier

Create a shell verifier with self-tests. For a supplied APK and expected values,
it must check:

- `apksigner verify --verbose --print-certs` succeeds;
- signer SHA-256 equals a protected expected release certificate fingerprint;
- the fingerprint is not accepted from the APK itself and no fallback value is
  embedded in source;
- package/application ID is `com.twinotify.app`;
- a production JS bundle exists inside the archive, so Metro is unnecessary;
- the release manifest has zero debug E2E receiver/provider components;
- APK SHA-256 and full Git commit match provided provenance;
- malformed archive, debug/unexpected certificate, missing bundle, mismatched
  commit/SHA, and E2E component presence all fail.

Self-tests may generate temporary fixture keys and APK-like fixtures only in a
temporary directory. The normal verifier must reject key/fingerprint override
modes intended for self-test.

### Step 3: Add a protected manual/tag build workflow

The workflow must:

1. use read-only repository permissions and pinned actions;
2. run Plan 003 host verification before building;
3. authenticate to EAS through a protected secret;
4. build `release-apk` and `production` non-interactively at the exact checkout
   commit;
5. download artifacts into a fresh runner directory;
6. run the standalone verifier with the protected expected certificate
   fingerprint;
7. create `app-provenance.json` from the actual bytes and commit;
8. create/sign `app-attestation.json` with the protected private key matching
   the committed public key;
9. upload APK, AAB, provenance, attestation, and detached signature with explicit
   retention and no raw logs containing credentials.

Use environment protection/approval. Do not auto-submit. Do not make this
workflow a normal untrusted pull-request job because secrets must never be
available there.

### Step 4: Connect the release evidence handoff

Document the exact operator flow:

- download the protected APK/provenance/attestation set;
- install the APK on the two release devices;
- collect the already specified private physical evidence;
- place only allowlisted artifacts into the evidence directory;
- run `make release-audit RELEASE_EVIDENCE_DIR=...` from the exact commit.

The release verifier must continue to reject missing `all-correctness`, stress,
battery, OEM, or physical evidence. This plan produces the candidate artifact;
it does not manufacture device results.

## Test plan

- EAS config resolves `release-apk` to APK and production to app-bundle.
- Standalone verifier positive fixture and all negative cases listed in Step 2.
- Workflow structural test: pinned actions, protected trigger/environment,
  required host gate, both builds, verifier, attestation, artifact upload.
- Existing release evidence self-test remains green.
- On an authorized release run, install the resulting APK with Metro stopped and
  prove app startup before beginning physical scenarios.

## Done criteria

- [ ] A protected workflow produces a release-signed APK and store AAB from one commit.
- [ ] The APK starts without Metro and contains no debug E2E components.
- [ ] Signer identity is compared with a protected expected fingerprint.
- [ ] Provenance and signed attestation match actual APK bytes and commit.
- [ ] No secret or private key is committed or printed.
- [ ] Release audit remains fail-closed for missing physical evidence.
- [ ] All host/config/verifier gates pass.
- [ ] README status is updated.

## STOP conditions

- The protected Android signing credential for `com.twinotify.app` is missing or
  its ownership cannot be established.
- The private attestation key matching the committed public key is unavailable.
- The release certificate fingerprint cannot be supplied through a protected
  environment.
- EAS resolves either release profile to a development client or debug signing.
- A requested change would expose secrets to pull-request code or logs.

## Maintenance notes

Rotate/recover signing and attestation credentials only through the protected
release process. Changing the Android signing identity breaks upgrades for
installed users. Keep installable APK verification separate from Play AAB
submission, but require both artifacts to originate from the same commit and
release configuration.
