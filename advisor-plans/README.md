## Current product truth

Direct LAN, relay fallback, route UX, durable local unpair, authenticated
control custody, v2 expiry, call opt-in/admission, bounded per-canonical capture,
permission-aware materialization, supersession terminalization, the eleven-child
LAN aggregate, and the Handoff Trace UI are implemented. Current host/native/UI
gates and independent reviews are green at `f119224`.

This is not a release-complete claim. The aggregate and release harness still
have explicitly pending physical two-phone, no-uplink, OEM/Doze,
reverse-direction, restart/failover, battery, and real-call proof. Never convert
those pending items into a pass without the corresponding private device
evidence.

The protected Android producer remains externally blocked on the intended EAS
project link and owner-controlled signing, token, certificate, and attestation
inputs. Local bundled APKs are QA artifacts, not protected release candidates.

## 2026-08-27 current-HEAD findings

### [PERFORMANCE-03] Permission-held mirrors are rescanned on unrelated traffic

- **Evidence**: `ReliableDeliveryDao.pendingMaterialization` admits current
  `PERMISSION_BLOCKED` retries unconditionally; `InboundDispatcher` requests a
  materialization pass after each committed notification/call; foreground also
  requests a pass while effective permission is false.
- **Impact**: permission denial can turn routine ingress into repeated O(N)
  platform attempts and retry writes, yielding O(N²) work across a burst.
- **Plan**: 020. **Confidence**: HIGH.

### [PERFORMANCE-04] Platform work runs inside the global inbound state mutex

- **Evidence**: notification and call branches invoke
  `NotificationMaterializer.materializePending()` before returning from
  `stateMutex.withLock`; that path performs Room, crypto, bitmap, and Android
  notification work.
- **Impact**: one slow platform effect serializes unrelated call and notification
  ingress and can backpressure the bounded relay route.
- **Plan**: 021. **Confidence**: HIGH.

### [TECH-DEBT-02] Distinct canonical capture lanes remain process-unbounded

- **Evidence**: Plan 016 bounds each lane to head/latest, but `lanes` and
  `deferredUntilPaired` can still retain one lane, coroutine, and command per
  distinct canonical ID. Listener callbacks currently throw if admission fails.
- **Impact**: an unpaired interval or prolonged persistence outage can cause
  unbounded process growth; a naive cap would crash the listener or lose final
  desired state.
- **Plan**: 022. **Confidence**: HIGH.

### [DOCS-02] Contributor and release examples contradict live product contracts

- **Evidence**: `mobile/README.md` is Expo starter boilerplate; `proto/README.md`
  describes v1 and a nonexistent Desktop Rust client; the release manifest
  example omits mandatory `PHY-CALL-01`.
- **Impact**: contributors enter unsupported Expo Go/reset workflows and release
  operators can copy an example the verifier rejects.
- **Plan**: 023. **Confidence**: HIGH.

### [DX-02] CI repeats heavyweight mobile verification

- **Evidence**: E2E Android runs `make verify`, direct `mobile-verify`, then the
  prerequisite-heavy `e2e-emulator`; protected release runs `npm ci` before
  `host-verify`, which runs `npm ci` again.
- **Impact**: duplicate installs/prebuilds/native gates add time, network/cache
  churn, and timeout risk without coverage.
- **Plan**: 024. **Confidence**: HIGH.

## 2026-08-27 findings summary

### [SECURITY-02] User app filters fail open after mutation

- **Evidence**: `AppFilterStore.add/remove/clear` commit then set the only
  callback cache to null; `TwinotifyNotificationListener` interprets null as an
  empty user denylist.
- **Impact**: content from apps the user explicitly blocked can be mirrored.
- **Plan**: 011. **Confidence**: HIGH.

### [BUG-06] Established LAN I/O failure can kill all delivery

- **Evidence**: `TransportCoordinator.run` catches route-open failures but not
  failures from its authenticated `carry`/pump; `SyncService` does not restart
  the failed transport child.
- **Impact**: relay fallback never runs and durable work stalls until service
  restart.
- **Plan**: 012. **Confidence**: HIGH.

### [BUG-07] Android does not enforce v2 expiry off relay

- **Evidence**: authenticated envelopes are not compared with current time and
  active expired outbox rows remain selectable on LAN.
- **Impact**: expired notification state can be applied or retried indefinitely.
- **Plan**: 013. **Confidence**: HIGH.

### [BUG-08] Snapshot failures can receive custody and relay controls never ACK

- **Evidence**: snapshot exceptions are swallowed before returning Accepted;
  peer receipts and snapshot controls never enter the only READY relay-ACK
  journal path. Conflicting peer-receipt transitions are also ignored.
- **Impact**: direct convergence controls can be lost, while relay mailbox
  controls redeliver until expiry.
- **Plan**: 014. **Confidence**: HIGH.

### [BUG-09] Native call sync is not a usable or fully contract-correct feature

- **Evidence**: no TypeScript or UI enablement/permission surface exists;
  mirrored calls use the default-importance channel; lower/conflicting call
  sequences are accepted; off-hook-first fabricates outgoing direction; release
  evidence requires no real call.
- **Impact**: normal users cannot enable call sync and existing proof cannot
  support a complete call-sync claim.
- **Plan**: 015. **Confidence**: HIGH.

### [BUG-01] Let offline-only pairs unpair locally

- **Evidence**: `mobile/modules/twinotify-core/android/src/main/java/co/twinotify/core/TwinotifyCoreModule.kt:459-493` marks revocation, then requires `config.relayUrl` whenever a peer exists. `mobile/modules/twinotify-core/android/src/main/java/co/twinotify/core/storage/PeerStore.kt:15-20` shows an offline-created peer can instead be identified by a non-null LAN binding.

- **Effort**: S. **Risk**: MED because relay revocation must remain fail-closed. **Confidence**: HIGH.

### [TESTS-01] Stop Android E2E from passing unsupported or fabricated scenarios

- **Evidence**: `e2e/internal/scenario/executor.go:93-100` returns unsupported for major actions and treats broad action-name classes as successful no-ops. `e2e/internal/scenario/scenario.go:39-42` encodes updates as `n1:v1`, `n1:v2`, `n1:v3`, while `executor.go:66-75` uses each whole suffix as a different notification tag. `e2e/scripts/run-two-emulators.sh:169-175` writes static pass JSON after execution.
- **Impact**: The suite can claim correctness without exercising the claimed transition, and the default `all-correctness` scenario contains actions that cannot run.
- **Effort**: M. **Risk**: MED. **Confidence**: HIGH.

### [DX-01] Make the real host contract mandatory

- **Impact**: Security-boundary, pairing-flow, and host-runner regressions can merge while all required PR checks remain green.

### [SECURITY-01] Replace debug-signed release output with a protected standalone artifact

## Findings considered and rejected or deferred

- **Direct LAN transport**: this historical deferral was superseded by the
  implemented live-LAN plans and commits. Current source follow-ups are Plans
  020-024; the physical and protected-release matrix remains separately pending.
- **Expo/Metro dependency audit**: `npm audit --omit=dev` reports high/critical
  advisories largely through Expo, Metro, React Native tooling, and
  `react-devtools-core`. A direct app-runtime exploit path was not established,
  and suggested remediation requires a major Expo migration. Defer to a bounded
  Expo/RN upgrade audit after release and direct-LAN work.
- **Split `TwinotifyCoreModule.kt` and `ReliableDeliveryDao.kt`**: both are large,
  but current correctness work has clearer user value and lower refactor risk.
- **Compound Room indexes**: several hot queries lack compound indexes, but no
  measured query-plan or latency regression was captured. Add instrumentation
  before proposing a Room 7-to-8 migration.
- **Relay startup mailbox validation**: startup performs a global retained-store
  validation under a Bolt write transaction. It is a plausible scale risk, but
  no production-size startup budget or regression was available, so it is not a
  higher-confidence plan than 020-024.
- **Duplicate notification-channel lookup**: `DefaultAndroidNotificationPort`
  and `MirrorPoster` both call `ensureChannels`; valid small optimization, but it
  does not outrank the bounded-work and CI items above.
- **Physical no-uplink acceptance**: pending by design until the operator returns
  with two available phones and a safe network-isolation path. It is evidence
  work, not a source-code finding to fake around.

### [BUG-02] Preserve retryable legacy v1 deliveries

- **Evidence**: `mobile/modules/twinotify-core/android/src/main/java/co/twinotify/core/service/InboundDispatcher.kt:50-69` records `msgId` before peer lookup, local key access, decryption, or plaintext JSON parsing.
- **Impact**: A temporary missing peer or keystore/decryption failure makes relay redelivery look like a replay for 48 hours, silently losing the notification.
- **Effort**: M. **Risk**: MED because the marker must remain before destructive inner side effects. **Confidence**: HIGH.

### [TESTS-02] Compile Android instrumentation sources in native gates

- **Evidence**: `Makefile` and `.github/workflows/mobile.yml` run `lintDebug testDebugUnitTest assembleDebug` but omit `compileDebugAndroidTestKotlin`, while Keystore, Room, offline-pairing, debug-security, and call-notification tests live under `src/androidTest`.
- **Impact**: Instrumentation source/API regressions can merge even though the native PR gate is green.
- **Effort**: S. **Risk**: LOW. **Confidence**: HIGH.

### [BUG-03] Keep call rows outside notification snapshots

- **Evidence**: `SnapshotCoordinator.localDigest` includes every active canonical row while emitted snapshot items come only from the notification listener; `ReliableDeliveryDao.beginSnapshot` and `commitSnapshot` likewise baseline and cancel every active canonical row, including `call:*`.
- **Impact**: An active call can invalidate notification repair or be cancelled as missing by a notification-only snapshot.
- **Effort**: S. **Risk**: MED because digest and reconciliation scope must change together. **Confidence**: HIGH.

### [BUG-04] Seal terminal call identity before persistence succeeds

- **Evidence**: `CallStateCoordinator` clears its session UUID only in `finalizeEvent()` after idle persistence succeeds. A failed idle followed by a new ringing/off-hook callback therefore reuses the completed UUID at a higher sequence.
- **Impact**: The receiver can accept the higher sequence and resurrect a terminal call under the old canonical ID.
- **Effort**: S. **Risk**: MED because queued terminal delivery must not clear a newer session. **Confidence**: HIGH.

### [BUG-05] Recover active call mirrors after process death

- **Evidence**: call UUID/sequence are in-memory, while a locally owned `call:*` canonical row remains ACTIVE until idle and its outbox row commit atomically. `SyncService` currently registers telephony capture without reconciling those durable ACTIVE rows.
- **Impact**: process death during ringing/active can strand the peer's ongoing call mirror indefinitely, and a restarted physical call can begin without closing the old logical session.
- **Effort**: M. **Risk**: HIGH because recovery must precede new capture and remain idempotent under stale concurrent commits. **Confidence**: HIGH.
